No identity

Nothing says these five are the same memory. Copy twice and you have two.

No provenance

Did you say it, or did a model infer it from a lockfile? After a copy, nobody can tell.

No lifecycle

Delete it in one tool and an old backup puts it straight back in another.

Every harness already does memory. They just picked different file names: AGENTS.md, MEMORY.md, USER.md, HUMAN.md. Conventions, not a contract.

Stay concrete: these are illustrations of the conventions, not vendor exports. The point isn't that any one shape is bad — it's that nothing ties them together. Three missing things: identity, provenance, lifecycle. Every later slide maps to one of those three.
02 · Evidence

"We have an export" is not the same as "it survived the trip."

A field report from the working group (PR #12, Oct 2): one Hermes agent's memory — MEMORY.md, USER.md, and 204 retrieval chunks — round-tripped through an existing portable format.

204/204

chunks came back with the same id and text

Markdown files byte-identical. Re-import was idempotent. The signature caught a one-byte change.

204/204

lost their ingestion time

One source document, ingested on 10 different dates. Chunk records had no time field.

208 → 0

"applied" — and none were stored

The import report counted what it was handed, not what it persisted. No warning.

Bytes surviving is the easy part. Time, ownership, and an honest receipt are what break — and they're exactly what a protocol can require.

Credit the Self-Improving Society team who measured this. Note it's a good format that mostly worked — that's the point: even good formats lose the metadata that matters. Also: the Markdown adapter merged §-separated entries into one. These findings became three things in v0.2: created_at on every record, owner/scope in interchange, and import receipts (§8.4).
03 · Why a shared format

Pairwise converters grow with the square. A shared format grows linearly.

132one-way converters,
each written for one pair
24adapters: one import
and one export per tool
12 = the coding-agent harnesses our ACP memory-server prototype already reads (Claude Code, Codex, goose, Cursor, Cline, Roo, Kilo, Zed, Gemini CLI, Qwen Code, Continue, Aider).
Drag the slider. n(n−1) one-way converters vs 2n adapters. The bigger argument isn't the count — it's who writes them. With pairs, the two biggest vendors decide whether you can leave. With a shared format, any small tool that writes one adapter joins the whole network.
04 · What it is (and isn't)

A transfer format, not a storage format.

OMP standardizes

1. An exchange format — what metadata travels with a memory so another system can import it and represent it well.
2. Runtime plug-in points — the shape of what crosses into an agent, so memory systems and harnesses can be chosen independently.

Constraint: everything must work from a folder of files on one laptop up to a multi-user deployment with access control.

Left to you to compete on

Storage, indexing, embeddings · recall signatures, ranking · confidence and decay scoring · federation merge logic · consolidation and "dream" agents · access-control languages · how forgetting is implemented.

Markdown is neither required nor preferred. The body is any text format, declared by media_type.

Three goals judge every field: adoption (a folder of markdown conforms with little work), auditability (when a deployment needs it — tiered, not forced on individuals), room for innovation (standardize shapes, not algorithms).

This scope came out of the Oct 14 technical working meeting. The "folder on a laptop" constraint is the one that kills most enterprise-shaped proposals, deliberately. If someone asks "why not just use X database's export" — that's a storage format; we're defining the boundary between stores.
05 · The object · §2–3

A memory is metadata plus a body. Three fields are required.

---
identifier: MEMORY.md
media_type: text/markdown
created_at: 2026-10-14T00:00:00Z
---

The user prefers concise answers.

The smallest conforming memory (Appendix C). No provenance means author unknown — a receiver MUST NOT read it as the user's own words.

FieldTierWhy it travels
identifierrequiredStable across versions. With origin, a global key.
media_typerequiredMarkdown, JSON, HTML, CSV, XML… not an ontology.
created_atrequiredWhen the system learned it.
valid_from / valid_untiloptionalWhen it's true. valid_until may be in the future.
provenanceauditEveryone and everything that contributed.
version · checksumauditOpaque version + declared comparator; integrity hash.
scopeACLTags access policy attaches to. Set by the system, never the agent.
path · title · tags · stuboptionalFolder structure is progressive-disclosure information.
evidence · linksoptionalWhy to believe it · how it relates to other memories.
anything elsepreservedUnknown fields MUST survive export.
The two-time-axis distinction is the one people miss: created_at = when the system recorded it; valid_from = when it became true in the world. "Status updates move to Friday" might be recorded Sep 15 but valid from Sep 15 or retroactively. Tier assignments are editors' proposals, except version and updated_at which were read back on Oct 14. The unknown-fields rule is what lets vendors innovate without breaking the round trip.
06 · Identity · §8.1

Two people each export a MEMORY.md. Which one is which?

manifest.json

{
  "protocol_version": "0.2",
  "profiles": ["minimal"],
  "origin": "store:6f1c2a9e-…-3d8e5a7b0c42",
  "exported_at": "2026-10-20T09:00:00Z",
  "selection": "snapshot",
  "intent": "copy",
  "media_types": ["text/markdown", …]
}

origin + identifier = the global key

Same idea as CloudEvents' source + id. origin is generated once per store, so colliding filenames stop colliding.

exported_at orders exports

It's how a receiver proves an archive predates a forget — the anti-resurrection demo in a few slides depends on it.

selection + intent

Snapshot, selection, or full history · copy, move, or federation. Absence from a partial export MUST NOT be read as deletion.

Open issue I-8: on import, does the receiver keep the origin identifier or mint its own with a recorded mapping? Either way the origin key survives because it's in the manifest. "move" means the source deletes only after a durable, conforming import on the other side.
07 · Live · the power of a portable format

One export. Five tools. Zero pairwise converters.

Walk all five tabs on the same 9 records. Markdown folder: Packer's loading profile — root files load at start, deeper ones are deferred. Graph: links become edges; evidence pointing outside the store is drawn hollow (dangling, kept, not dropped). Search: type "friday", toggle "current only" — valid_until and supersession filter results (§6.3). Agent context: the runtime projection drops checksum, scope, audit fields — show the size difference. Auditor: computes the profiles this export can actually claim and re-hashes checksums in the browser. Then invite someone to AirDrop their MEMORY.md/AGENTS.md — drop it; it becomes minimal-profile records instantly, and the auditor tells them exactly what's missing for audit. 09 · Provenance & accuracy · §4

  
Provenance is a list of contributors — not a grade.

  

    

    

      
A person asked, an agent wrote, a person approved
A plain list records that without forcing one "human / AI" label on the result. Maintenance agents (forget, consolidation) are writers too and MUST appear.

      
No standard confidence score [editors' proposal · I-20]
A score can't move between systems unless the algorithm moves too, and self-reinforcing loops make systems confidently wrong. Instead: who checked it is provenance (verified, corrected, contradicted); what the check rests on is evidence. Receivers compute their own confidence.

      
Accountable human, only where it matters
The audit profile needs one kind: human per memory. For a nightly consolidator, that can be the operator who runs it. A store that can't name one is still conforming — it just can't claim audit.

    

  

  
"Vouching" came from the Oct 14 meeting: rather than "0.87 confident", say who vouched and on what basis. Cognee's PR #16 proposes an accuracy field — that's a live disagreement and one of the issues for the room. Also §4.5: v0.1 allowed heuristic provenance; v0.2 says leave it out rather than guess, because a receiver can't tell a guess from a fact.







  
10 · Live · receipts · §8.4

  
Import into three stores. Trust the receipt, not the progress bar.

  

    
    
    
    Runs on whatever collection is loaded — including yours.
  

  

    

    

  

  
Conforming: everything accepted, unknown x_ fields kept. Typical: mints new IDs without a mapping, keeps title and body — the receipt lists every dropped field, so the loss is visible before anyone relies on it. Optimistic: reproduces the 208→0 bug: the report says "applied" from the input while the store kept nothing. The rule: receipts are computed from what was persisted. Retries MUST NOT duplicate memories.







  
11 · Live · forget & anti-resurrection · §6.5

  
Forget something. Then try to bring it back from an old backup.

  

    

    

      
Tombstones (travel with exports, carry no content)

      

        
Re-import the archive exported at 

        

        

      

    

  

  
Forget a memory or two (try the Maya ownership one). The tombstone records who, when, why — and no content. Re-import the pre-forget archive into a naive store: resurrected. Into a tombstone-aware store: blocked, because origin+identifier matches and the archive's exported_at predates the forget. Raise I-7: editors propose this belongs in the audit profile, not core. Is that right? Wes's point from Oct 14: some deployments need immediate removal (classified data stored by mistake) regardless of retention rules.







  
12 · The messy edges · §8.5, §8.7

  
References break and provenance can be laundered. Plan for both.

  

    

      
Dangling references — hold, mark, don't fail

      
A link or evidence ref may point at a transcript that didn't travel, a deleted memory, a system of record, or something outside the reader's scope.

      
    
        
  • A system MUST keep them and mark them dangling.
    • 
        
  • An import MUST NOT fail because of one.
    • 
        
  • It MAY resolve them later — even by asking a person.
    • 
      

      
Our sample: 0 dangling refs, all retained. In the sample, the rate-limit memory links to the provider's docs instead of copying a number that will go stale.

    

    

      
Trust on import — a claim, not a fact [open · I-22]

      
You can't verify provenance recorded in a system you don't control. An imported chain is a claim made by the exporting origin.

      
    
        
  • checksum + history check integrity, not truth.
    • 
        
  • Receivers MAY review or sanitize before agents rely on imports.
    • 
        
  • Credentials are not memory and MUST NOT be exported.
    • 
      

      
Memory import is a prompt-injection surface. Third-party chains of trust are out of scope — for now.

    

  

  
Gabe (IBM) proposed the dangling-reference rules on Oct 14. The scope point matters: a reference that resolves for one person dangles for another, so dangling is a per-reader state. On trust: this is where security folks in the room should push. Is "receivers MAY sanitize" enough? Should the manifest be signed? PR #17 has a threat model draft.







  
13 · Runtime · conformance · §9–10

  
Standardize what crosses the boundary — not how recall works.

  

    
Files
The agent reads memory files with shell or file tools.

    
Tools
Explicit remember / recall tools from a memory server. MCP proposed as the binding — not agreed (I-10).

    
Hooks
A supervisor decorates the session and decides what to store, without the agent knowing.

  

  
The protocol MUST NOT fix a recall signature. It defines what recall returns: memory objects in the runtime representation. Claim only the profile you implement:

  

    
Minimal
3 required fields + body; unknown fields preserved. A folder of markdown gets here.

    
Markdown loading
Root MEMORY.md, deeper files deferred, selective reads. Declares any fields it drops.

    
Federation
Upload / search / read / delete + a capability endpoint. Read memory where it lives.

    
Audit
Provenance with an accountable human, checksum + version, immutable history, evidence on derived memories, tombstones.

  

  
Recall not standardized is [agreed] — implementations compete on retrieval. Federation binding is the AIDP/FMP endpoint set; the FMP demo in the repo is a Claude Code plugin plus two memory servers with different permission models. Under the thin-core proposal (I-21), each profile would become a named set of semantic conventions.

Status, honestly
v0.2 is an editors' draft (PR #13). Every MUST is proposed, not adopted. 20 issues still open. That's why we're here.

Under the markdown loading profile that projection should declare the loss (§10.2).
